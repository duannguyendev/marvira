====================================================
GAMEPLAY DATA MODEL (CRITICAL)
====================================================

EVENT STRUCTURE:
- An event has MANY ordered places (order_index 0, 1, 2, â€¦).
- Each place has exactly ONE question (via question_id).
- Questions live in a reusable bank and can be used in multiple events.

MOBILE GAMEPLAY (linear â€” API enforced):
1. If event is password-protected (join_password_hash IS NOT NULL), player MUST have access
   before gameplay: creator, user_event_access row, or existing user_event_progress (grandfathered).
   Other players call POST /events/:id/join with the password once; no re-prompt on return visits.
2. Player travels to Place #1 (first stop by order_index).
3. POST /places/:id/unlock â€” GPS must be within radius_meters; server rejects if no play access.
4. GET /places/:id/question â€” show question (no answer field); server rejects if no play access.
5. POST /places/:id/answer â€” on correct answer, response includes nextPlaceId; server rejects
   if no play access.
6. Repeat for Place #2, #3, â€¦ until event completed.

Progress is tracked via user_event_progress.current_place_index.
Players CANNOT skip ahead to later places until previous stops are completed.

PASSWORD-PROTECTED EVENTS (access model):
- join_password_hash null â†’ public event (default); all authenticated users may play.
- join_password_hash set â†’ private event; only users with play access may unlock/answer.
- Public API MUST expose isPasswordProtected (boolean) on event list/detail DTOs.
- Public API MUST NOT return join_password_hash or plain-text password.
- When JWT present, event detail MAY include hasAccess (boolean): true if public, creator,
  user_event_access grant, or grandfathered progress exists.
- GET /events/:id/places for private events without access: return redacted payload (e.g. place
  count only, no coordinates/questions) OR 403 â€” implementation MUST prevent map scraping
  before join.
- Rate-limit POST /events/:id/join (e.g. 5 failed attempts per user+event per 15 minutes via Redis).
- Wrong-password response MUST be generic ("Incorrect password"); do not leak event existence.

TIMING (for leaderboards and future rewards):
- Per place: answer_duration_ms = time from unlock to first correct answer at that stop.
- Per event: total_duration_ms = time from first unlock to final place completed.
- Progress starts on first unlock (no separate "start event" endpoint).

ADMIN DASHBOARD (non-linear â€” full visibility):
- Admin sees ALL places, coordinates, hints, and questions for an event at once.
- NO unlock restrictions on admin pages â€” configure the complete hunt trail.
- Sequential unlock applies ONLY in the mobile app via API calls.
- Event edit UI is PLACE-FIRST: each stop card shows location fields + inline question
  (add / edit / pick from library). Do NOT use a separate â€œevent questions poolâ€ as the
  primary admin workflow.
